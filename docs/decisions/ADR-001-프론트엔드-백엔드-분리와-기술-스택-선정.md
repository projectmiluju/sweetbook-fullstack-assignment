# ADR-001: 프론트엔드-백엔드 분리와 기술 스택 선정

**일자:** 2026-04-04
**상태:** Accepted

## 맥락 (Context)

이번 과제는 최종 사용자 UI와 별도 백엔드 서버를 요구한다. 또한 Book Print API의 `Books API`, `Orders API`를 실제 서비스 흐름 안에서 사용해야 하며, API Key는 서버에서만 관리해야 한다. 동시에 마감이 짧아 실행 절차와 제출 완성도도 중요하다.

## 고려한 선택지

### 선택지 A: Next.js + Express + TypeScript

- 장점: 프론트와 백엔드 책임이 분리되어 과제 요구사항을 설명하기 쉽다
- 장점: 프론트/백엔드를 TypeScript로 통일할 수 있다
- 장점: UI 개발 속도와 API 오케스트레이션 구현의 균형이 좋다
- 단점: 단일 앱 구조보다 초기 설정이 조금 더 복잡하다
- 단점: dev 스크립트와 README를 더 명확히 관리해야 한다

### 선택지 B: Next.js 통합형

- 장점: 초기 설정이 가장 단순하다
- 장점: 실행 명령과 배포 구성이 단순하다
- 단점: 별도 백엔드 서버를 분리해서 보여주기 어렵다
- 단점: 면접에서 아키텍처 책임 분리가 약하게 보일 수 있다

### 선택지 C: Next.js + FastAPI/Python

- 장점: 백엔드 로직을 Python으로 빠르게 작성할 수 있다
- 장점: 데이터 가공이 복잡할 때 유리하다
- 단점: 프론트와 언어가 달라져 문맥 전환 비용이 생긴다
- 단점: 이번 과제에서는 Node 생태계와의 연결성이 더 높다

## 결정 (Decision)

프론트엔드는 `Next.js + TypeScript`, 백엔드는 `Express + TypeScript`로 분리한다. 스타일링은 `Tailwind CSS`, 데이터 저장은 정적 더미 데이터로 시작한다. 외부 API 연동은 백엔드에서 직접 HTTP 호출로 구현하고, `Node.js SDK`는 참고 자료로만 활용한다.

## 결과 (Consequences)

- 긍정적: 과제 요구사항인 UI와 백엔드 서버 분리를 명확하게 만족한다
- 긍정적: 타입과 런타임을 통일해 구현과 디버깅 속도를 유지할 수 있다
- 긍정적: README와 면접 설명에서 구조적 근거를 제시하기 쉽다
- 부정적: 단일 앱 구조보다 초기 보일러플레이트가 늘어난다
- 부정적: 로컬 실행 시 프론트와 백엔드를 각각 실행해야 한다
- 리스크: 구현 초반에 환경 설정이 불완전하면 실제 기능 구현보다 세팅에 시간을 쓸 수 있다

## 되돌릴 조건 (Reversal Triggers)

- 프론트/백엔드 분리로 인한 설정 비용이 과도해 핵심 흐름 구현이 지연될 때
- Express 서버 유지가 과제 범위 대비 불필요하게 무거워질 때
- 후속 PHASE에서 단일 서버 통합이 더 명확하다는 증거가 생길 때
