# 개발 일지: 책 종류 선택 흐름 연결 (#9)

**일자:** 2026-04-06
**관련 버전:** v0.1.0
**관련 역할:** build, qa

## 배경 (Context)

`/book-types` 페이지는 Foundation Set(#29)에서 골격만 잡힌 상태였다. 두 카드가 시각적으로는 존재했지만 CTA 버튼이 모두 `/dashboard`로 연결되어 있어 실질적인 분기가 없었다. 이슈 #9의 핵심 DoD인 "선택 상태가 다음 단계로 전달됩니다"가 미충족 상태였다.

## 문제 (Problem)

1. `book-types/page.tsx`의 CTA 두 개가 모두 `/dashboard`로 링크 — 선택해도 흐름이 이어지지 않음.
2. `searchParams.studentId`를 읽지 않아 어느 수료생 컨텍스트에서 진입했는지 알 수 없었음.
3. 선택 이후 도달할 "다음 단계" 페이지 자체가 없었음.

## 최종 해결 (Resolution)

### lib/book-types.ts 추출

`buildBookCreateHref`, `buildBookTypesBackHref`, `isValidBookType` 세 함수를 `apps/web/src/lib/book-types.ts`로 분리했다. 이 결정의 이유:

- 동일한 URL 패턴이 `book-types/page.tsx`와 `students/[studentId]/create/page.tsx` 양쪽에서 필요했다. 각 파일에 inline 로직을 두면 다음 이슈(편집 흐름)에서 세 번째 위치가 생길 때 패턴이 흩어진다.
- 단위 테스트 대상으로 만들기 위해서도 추출이 필요했다. Server Component 내부 함수는 직접 import해서 검증할 수 없다.

### book-types/page.tsx 수정

`searchParams: Promise<{ studentId?: string }>` prop을 추가했다. `buildBookCreateHref(studentId, bookTypeId)`로 CTA href를 구성해 각 버튼이 올바른 다음 단계로 연결되도록 했다. `studentId`가 없는 직접 진입의 경우 `/dashboard` fallback으로 처리한다.

### students/[studentId]/create/page.tsx 신규 생성

선택 확정 화면을 새로 만들었다. `params.studentId` + `searchParams.bookType`을 수신하며, 유효하지 않은 `bookType`은 즉시 `notFound()`로 처리한다. 수료생 데이터와 선택한 책 종류를 함께 보여주고, "책 만들기" 버튼은 편집 기능이 아직 미구현임을 명시하며 disabled 처리했다 — 다음 이슈에서 활성화할 자리를 남겨두는 방식이다.

## 배운 것 (Lessons Learned)

Server Component의 순수 로직(URL 구성, 유효성 검사)은 초기부터 lib 레이어로 분리해두는 것이 테스트 가능성과 재사용성 양쪽에서 유리하다. 이번에는 이미 inline 구현 후 추출했지만, 다음 이슈부터는 URL 패턴 로직은 처음부터 lib에 두고 page에서 참조하는 방식으로 가는 것이 좋다.

"편집 기능 준비 중" disabled 버튼 패턴은 다음 단계의 기능 경계를 UI에서 명시적으로 드러내는 역할을 한다. 단순히 버튼을 숨기는 것보다 진입점이 어디인지 심사자가 파악하기 쉽다.
