## 0. 문서 상태

이 문서는 스위트북 개발 과제 PDF와 사용자 대화를 기준으로 작성한 PRD이다. 초기에는 가정을 포함해 시작했지만, 현재 문서는 사용자와 합의한 방향을 반영한 구현 기준 문서다.

### ⚠️ 가정 (Assumptions)

- 서비스 주제는 `부트캠프 운영자용 수료 포트폴리오 북 제작 서비스`로 고정한다.
- 핵심 가치는 `교육기관이 수료생의 프로젝트와 성장 기록을 책으로 제작해 전달하는 경험`으로 본다.
- 인증/회원가입/결제는 과제 범위에서 제외한다.
- 데이터 저장은 레포 내 더미 데이터 중심으로 제한한다.
- `개인 포트폴리오 북`과 `기수 쇼케이스 북`을 모두 MVP 범위에 포함한다.
- 편집 기능은 제공하되, 전문 출판 편집기 수준의 완전 자유 배치가 아니라 `블록 기반 편집 + 페이지 순서 변경`으로 제한한다.
- 템플릿 탐색/선택 기능은 사용자에게 제공하지 않으며, 구현에 필요한 `templateUid`는 내부 설정값으로 고정한다.

## 1. 개요 (Overview)

- **배경 및 목적:** 스위트북의 Book Print API는 메일 본문 기준 `B2B API 플랫폼` 맥락을 가진다. 따라서 이번 과제는 단순 소비자 앱보다, 사업자가 자기 고객 경험에 책 제작 기능을 붙이는 B2B2C 시나리오가 더 적합하다. 본 서비스는 부트캠프 운영자가 수료생의 결과물을 책으로 제작해 전달하는 흐름을 구현한다.
- **타겟 워크플로우:** 운영자는 기수 데이터를 확인하고, 개인 수료 포트폴리오 북 또는 기수 쇼케이스 북을 선택해 콘텐츠를 편집한 뒤 책을 생성하고 주문한다. 최종 사용자는 수료생, 학부모, 채용 파트너, 데모데이 참석자이며, 책은 수료 기념품이자 성과 아카이브, 대외 공유용 자료 역할을 한다.

## 2. 한 줄 서비스 정의

부트캠프 운영자가 수료생의 프로젝트, 기술 스택, 회고, 멘토 피드백을 모아 `수료 포트폴리오 북`을 자동 생성하고 주문할 수 있는 웹앱

## 3. 핵심 사용자

### 3.1 1차 사용자: 부트캠프 운영자

- 기수별 수료생 데이터를 관리한다
- 특정 수료생의 책을 생성하고 주문한다
- 부트캠프 브랜딩이 들어간 결과물을 원한다

### 3.2 2차 사용자: 수료생

- 자신의 성장 기록이 정리된 결과물을 받는다
- 취업/데모데이/포트폴리오 보조 자료로 활용한다

- [ ] 운영자는 생성된 책 결과를 UI에서 확인할 수 있다
- [ ] 운영자는 생성된 책으로 주문 요청을 할 수 있다

- [ ] 운영자는 주문 성공/실패 결과를 UI에서 확인할 수 있다

## 6. 책 종류

### 6.1 개인 수료 포트폴리오 북

- 대상: 수료생 1명
- 목적: 수료 기념, 개인 성과 아카이브, 대외 소개용
- 필수 콘텐츠: 자기소개, 브랜딩된 기념 수료 페이지, 기술 스택, 대표 프로젝트, 회고, 멘토 코멘트, 활동 사진

### 6.2 기수 쇼케이스 북

- 대상: 기수 전체
- 목적: 데모데이 배포, 채용 파트너 전달, 부트캠프 브랜딩
- 필수 콘텐츠: 기수 소개, 과정 소개, 수료생 요약 페이지, 대표 프로젝트 하이라이트, 운영진 메시지, 활동 사진

## 7. 왜 책이어야 하는가

- 단순 수료증은 한 장 문서로 충분하지만, `프로젝트`, `기술 스택`, `회고`, `멘토 코멘트`, `활동 사진`까지 포함하면 책 형식이 자연스럽다
- 교육기관 입장에서는 기수 성과를 브랜딩된 인쇄물로 남길 수 있다
- 수료생 입장에서는 수료 기념품이자 대외 공유용 포트폴리오 보조 자료가 된다
- 파트너 채용사/데모데이 관계자에게 전달 가능한 물리적 결과물이 된다

## 8. 편집 정책

### 8.1 허용 편집

- 표지 제목/부제 수정
- 브랜딩된 기념 수료 페이지 문구 수정
- 블록 단위 텍스트 수정
- 대표 프로젝트 포함/제외
- 프로젝트 순서 변경
- 사진 포함/제외 및 순서 변경
- 페이지 순서 변경
- 테마 선택

### 8.2 제외 편집

- 캔버스 위 완전 자유 배치
- 폰트/여백/색상 무제한 세부 조정
- 무제한 임의 컴포넌트 추가
- 전문 출판 편집기 수준의 자유 레이아웃 도구

### 8.3 편집 단위

- 기본 편집 단위는 `블록`
- 상위 정렬 단위는 `페이지`
- 즉, `블록 기준 편집 + 페이지 순서 변경`을 이번 MVP 기준으로 본다

## 10. 사용자 시나리오 (Happy Path)

1. 운영자가 웹앱에 접속한다.
2. 특정 기수를 선택한다.
3. `개인 포트폴리오 북` 또는 `기수 쇼케이스 북`을 선택한다.
4. 대상 수료생 또는 기수 전체 데이터를 확인한다.
5. 편집 화면에서 블록 내용을 수정하고 페이지 순서를 조정한다.
6. `책 만들기` 버튼을 누른다.
7. 서버는 편집 결과를 Book Print API 요청 포맷으로 변환한다.
8. 서버는 `Books API`를 호출한다.
9. 프론트는 책 생성 결과를 보여준다.
10. 운영자는 주문 요청을 진행한다.
11. 서버는 `Orders API`를 호출한다.
12. 프론트는 주문 결과를 보여준다.

### 11.2 상태 전이도

- **목록 로딩:** `Idle → Loading → Success | Error`
- **편집:** `Idle → Editing → PreviewReady`
- **책 생성:** `Idle → Submitting → Success | Error`
- **주문 생성:** `Idle → Submitting → Success | Error`

### 11.3 내부 앱 API 엔드포인트 (예상)

| 메소드 | 경로 | 용도 |
|--------|------|------|
| `GET` | `/api/cohorts` | 기수 및 수료생 목록 조회 |
| `GET` | `/api/students/:id` | 수료생 포트폴리오 상세 조회 |
| `POST` | `/api/books` | 선택한 책 유형과 편집 데이터로 책 생성 |
| `POST` | `/api/orders` | 생성된 책으로 주문 생성 |

### 11.4 외부 API 사용 계획

| API | 사용 여부 | 용도 |
|-----|----------|------|
| `Books API` | 필수 | 수료 포트폴리오 북 생성 |
| `Orders API` | 필수 | 생성된 책 주문 |
| `BookSpecs API` | 강하게 권장 | 판형 선택, 페이지 규칙 검증 |
| `Credits API` | 강하게 권장 | 주문 가능 잔액 확인 |

## 12. 예외 처리 정책 (Exception Handling)

| 상황 | 대응 방안 | 우선순위 |
|------|---------|---------|
| 첫 실행 시 데이터 0건 | 기본 더미 기수/수료생 데이터를 제공한다 | 높음 |
| 외부 API 500/네트워크 오류 | 실패 메시지와 `다시 시도` 버튼 제공 | 높음 |
| 운영자가 책 생성 버튼을 연속 클릭 | 버튼 비활성화 및 중복 요청 방지 | 높음 |
| 주문 전에 책 생성이 완료되지 않음 | 주문 버튼 비활성화 | 높음 |
| 편집 중 페이지 순서가 비정상 상태가 됨 | 기본 템플릿 순서로 복구하는 기능 제공 | 중간 |
| 블록 편집값 일부 누락 | 기본 텍스트 fallback 사용 | 중간 |
| 잘못된 수료생 상세 URL 접근 | 404 또는 목록 복귀 유도 | 중간 |
| API Key 누락 | 서버 시작 시 명시적 에러 출력 | 높음 |
| 포트폴리오 데이터 일부 누락 | 필수 필드만 검증하고 누락 항목은 대체 문구 처리 | 중간 |
| 프로젝트 수가 많아짐 | MVP에서는 상위 2~3개 프로젝트만 사용 | 낮음 |

## 13. 권한 정책 (Permissions)

## 14. 동시성/경합 정책

## 22. 공식 API 문서 기반 구현 제약

아래 내용은 2026-04-04 기준 SweetBook 공식 문서를 확인해 반영한 것이다.

### 22.1 실제 생성 흐름

이번 과제에서 사용자가 체감하는 `책 생성`은 내부적으로 아래 순서를 거친다.

1. `POST /v1/books` 로 빈 책 초안 생성
2. 내부에 고정한 표지용 `templateUid`로 `POST /v1/books/{bookUid}/cover` 호출
3. 내부에 고정한 내지용 `templateUid`로 `POST /v1/books/{bookUid}/contents` 를 여러 번 호출해 내지 추가
4. `POST /v1/books/{bookUid}/finalization` 으로 최종화
5. `POST /v1/orders` 로 주문 생성

즉, PRD 상의 `POST /api/books`는 실제로는 여러 외부 API 호출을 오케스트레이션하는 서버 작업이어야 한다.

### 22.2 Books API 최소 필드

#### 1) 초안 책 생성

- 엔드포인트: `POST /v1/books`
- 필수 필드:
  - `title`
  - `bookSpecUid`
- 선택 필드:
  - `specProfileUid`
  - `externalRef`
- 권장 헤더:
  - `Authorization: Bearer <API_KEY>`
  - `Idempotency-Key`

#### 2) 표지 생성

- 엔드포인트: `POST /v1/books/{bookUid}/cover`
- 형식: `multipart/form-data`
- 필수 필드:
  - `templateUid`
- 선택 필드:
  - `parameters` JSON 문자열
  - 템플릿 변수명과 일치하는 이미지 파일 필드

#### 3) 내지 추가

- 엔드포인트: `POST /v1/books/{bookUid}/contents`
- 형식: `multipart/form-data`
- 필수 필드:
  - `templateUid`
- 선택 필드:
  - `parameters` JSON 문자열
  - 템플릿 변수명과 일치하는 이미지 필드
  - 쿼리 파라미터 `breakBefore=page|column|none`

#### 4) 최종화

- 엔드포인트: `POST /v1/books/{bookUid}/finalization`
- 전제 조건:
  - 책 상태가 `draft`
  - 페이지 수가 판형 규칙의 최소/최대/증분 조건을 만족

### 22.3 Orders API 최소 필드

- 엔드포인트: `POST /v1/orders`
- 필수 헤더:
  - `Authorization: Bearer <API_KEY>`
  - `Content-Type: application/json`
  - `Idempotency-Key`
- 필수 바디:
  - `items`
  - `items[].bookUid`
  - `items[].quantity`
  - `shipping`
  - `shipping.recipientName`
  - `shipping.recipientPhone`
  - `shipping.postalCode`
  - `shipping.address1`
- 선택 바디:
  - `shipping.address2`
  - `shipping.memo`
  - `externalRef`
  - `externalUserId`

### 22.4 판형 제약

- `bookSpecUid`는 책 생성 시 필수다
- 판형별 페이지 규칙이 있어 최종화 전에 페이지 수를 맞춰야 한다
- 공식 예시 기준 `PHOTOBOOK_A4_SC`는 `24~130페이지`, `2페이지 단위 증가`다
- 따라서 이번 서비스는 `편집 결과를 자유 페이지 수로 두는 것`이 아니라, 최종화 가능한 페이지 수 규칙에 맞춰 자동 보정해야 한다

### 22.4-1 기본 판형 결정

- 실제 Sandbox 연결 테스트 결과 이번 MVP의 기본 판형은 `PHOTOBOOK_A4_SC`로 고정한다
- 이유: `BookSpecs API`에서 페이지 규칙이 명확히 확인됐고, 현재 공용 템플릿 및 샘플 운영 흐름과도 가장 무난하게 맞기 때문이다

### 22.5 이미지 제약

- 이미지 파일 최대 크기: `50MB`
- 책당 최대 사진 수: `200장`
- URL 이미지 사용 시 다운로드 제한: `50MB`, `10초 타임아웃`
- 지원 포맷: JPEG, PNG, GIF, BMP, TIFF, WebP
- Photo Upload API 별도 안내에서는 jpg/jpeg/png/gif/bmp/webp/heic/heif 업로드를 지원한다고 명시되어 있으므로, 구현 시에는 `jpg/jpeg/png/webp` 중심으로 제한하는 것이 안전하다

### 22.6 멱등성 정책

- `POST /v1/books` 는 `Idempotency-Key` 지원
- `POST /v1/orders` 는 `Idempotency-Key` 사용이 사실상 필수
- 멱등성 문서 기준 동일 요청이 짧은 시간 내 중복 수신되면 `409 Conflict`가 날 수 있다
- 따라서 앱 내부에서도 `책 생성 중`, `주문 생성 중` 상태에서는 중복 클릭을 막아야 한다

### 22.7 이번 서비스에 대한 구현 판단

- 외부 API의 실제 요구사항을 보면, 이번 과제의 핵심은 `자유 편집 툴` 자체가 아니라 `편집 결과를 템플릿 기반 API 호출로 안정적으로 변환하는 서버 오케스트레이션`이다
- 따라서 편집 기능은 계속 유지하되, 결과 저장 구조는 `블록 데이터 → 고정 templateUid 파라미터` 매핑 중심으로 설계해야 한다
- 내부 `POST /api/books`는 다음 단계를 수행해야 한다
  - 책 초안 생성
  - `BookSpecs API` 기준으로 유효한 `bookSpecUid` 선택 또는 검증
  - 내부 고정 표지 템플릿 적용
  - 내부 고정 내지 템플릿 반복 적용
  - 페이지 수 규칙 검사
  - 최종화
- 내부 `GET /api/credits` 또는 주문 전 서버 검증 로직은 `Credits API`로 잔액 부족을 선제 차단해야 한다
- 내부 `POST /api/orders`는 FINALIZED 상태의 `bookUid`만 받도록 제한해야 한다

## 23. API 채택 결론

### 23.1 이번 과제에서 채택하는 API

- **필수 사용**
  - `Books API`
  - `Orders API`
- **강하게 권장하여 실제 채택**
  - `BookSpecs API`
  - `Credits API`

### 23.2 이번 MVP에서 제외하는 API

- `Templates API`
  - 이유: 사용자 기능으로 템플릿 탐색/선택이 핵심 가치가 아니고, 현재 주제와 공용 템플릿의 도메인 적합성도 낮다
- `Webhooks API`
  - 이유: 주문 상태 자동 반영까지 넣으면 과제 핵심보다 운영 기능이 커진다

### 23.3 템플릿 처리 방식

- `Templates API`를 제품 기능으로 사용하지 않더라도 `Books API`의 표지/내지 생성에는 `templateUid`가 필요하다
- 이번 구현에서는 사전 검증한 `templateUid`를 서버 상수 또는 설정 파일에 고정한다
- 즉 템플릿은 `동적 조회 대상`이 아니라 `내부 구현 의존성`으로 취급한다

## 23.4 SDK 사용 방침

- PDF 기준 SDK 사용은 필수가 아니라 선택 사항이다
- 이번 구현에서는 `Node.js` 스택을 선택했으므로 `Node.js SDK`를 참고 자료로 활용할 수 있다
- 다만 핵심 연동은 백엔드에서 직접 HTTP 호출로 구현한다
- 이유:
  - 현재 PRD에서 요구하는 `표지/내지/최종화/주문` 오케스트레이션을 직접 제어하기 쉽다
  - 디버깅과 에러 핸들링이 더 투명하다
  - README와 서술형 답변에서 근거 설명이 쉽다

### 24.3 페이지 수 보정 규칙

- 기본 목표는 두 책 모두 `24페이지`
- 실제 편집 결과가 `24페이지` 미만이면 아래 우선순위로 자동 보강한다
  - 사진 페이지 추가
  - 회고/인용문 확장 페이지 추가
  - 부트캠프 소개 또는 성과 요약 페이지 추가
- 실제 편집 결과가 `24페이지`를 초과하면 아래 우선순위로 축약한다
  - 선택형 부록 페이지 제거
  - 프로젝트 상세 페이지를 요약 페이지로 합치기
  - 사진 페이지 수 축소
- 최종 페이지 수는 반드시 `pageIncrement=2` 규칙을 만족해야 한다

## 25. 데이터 매핑 원칙

### 25.1 개인 북 매핑 원칙

- `student.name` → 표지 이름, 수료 페이지 이름, 소개 페이지 이름
- `cohort.name`, `cohort.program`, `cohort.graduationDate` → 표지 부제, 수료 페이지, 기관 소개
- `student.bio` → 자기소개 블록
- `student.techStack` → 기술 스택 블록
- `student.projects[]` → 프로젝트 요약/상세 블록
- `student.retrospective` → 회고 페이지
- `student.mentorComment` → 멘토 코멘트 페이지
- `student.photos[]` → 활동 사진 페이지
- `student.certificateMessage` → 브랜딩된 기념 수료 페이지 메시지

### 25.2 기수 쇼케이스 북 매핑 원칙

- `cohort.name`, `cohort.program`, `cohort.graduationDate` → 표지, 과정 소개, 기수 소개
- `cohort.students[]` → 수료생 리스트와 개인 포커스 페이지
- `students[].projects[]` → 대표 프로젝트 하이라이트
- `students[].techStack` 집계 결과 → 기술 스택 맵
- `students[].retrospective` 일부 발췌 → 회고 인용구 페이지
- `students[].photos[]` 집계 결과 → 데모데이/활동 사진 페이지

### 25.3 편집 저장 원칙

- 페이지 순서는 `EditSession.pages`에 저장한다
- 숨김 처리된 블록은 `EditSession.hiddenBlocks`에 저장한다
- 수정된 텍스트는 `EditSession.customText`에 저장한다
- 서버는 최종 생성 시 `원본 더미 데이터 + EditSession`을 합성해 외부 API 요청을 만든다

## 26. 내부 `/api/books` 요청 오케스트레이션 스펙

### 26.1 내부 요청 바디

프론트엔드는 외부 API 구조를 직접 알지 않고 아래 형태로 서버에 요청한다.

```json
{
  "bookType": "individual",
  "cohortId": "cohort-2026-01",
  "studentId": "student-001",
  "editSession": {
    "themeId": "default-a4",
    "pages": ["cover", "intro", "certificate", "bio", "stack", "project1-summary"],
    "hiddenBlocks": ["project3-detail"],
    "customText": {
      "coverTitle": "김코드의 수료 포트폴리오 북",
      "certificateMessage": "끝까지 완주한 성장을 축하합니다."
    }
  }
}
```

`bookType=cohort_showcase` 인 경우에는 `studentId` 없이 `cohortId`만 전달한다.

### 26.2 서버 오케스트레이션 순서

1. 요청 유효성 검사
2. `cohortId`, `studentId`, `bookType`에 맞는 원본 더미 데이터 조회
3. `EditSession` 병합
4. 페이지 구성표 기준으로 최종 페이지 목록 생성
5. `BookSpecs API` 기준으로 페이지 수 검증 및 보정
6. `POST /v1/books` 로 초안 책 생성
7. 고정 cover `templateUid`로 `POST /v1/books/{bookUid}/cover`
8. 페이지 목록을 순회하며 고정 content `templateUid`로 `POST /v1/books/{bookUid}/contents`
9. `POST /v1/books/{bookUid}/finalization`
10. 생성 결과를 내부 `BookJob` 형태로 반환

### 26.3 내부 고정 설정값

이번 MVP는 아래 값을 서버 설정으로 고정한다.

```json
{
  "defaultBookSpecUid": "PHOTOBOOK_A4_SC",
  "coverTemplateUid": "internal-fixed-cover-template",
  "contentTemplateUid": "internal-fixed-content-template",
  "defaultOrderQuantity": 1
}
```

실제 `templateUid` 값은 코드 저장소의 서버 설정 파일에서 관리한다.

### 26.4 `POST /v1/books` 생성 payload

```json
{
  "title": "김코드 수료 포트폴리오 북",
  "bookSpecUid": "PHOTOBOOK_A4_SC",
  "externalRef": "student-001-individual-20260404"
}
```

생성 시 `Idempotency-Key`는 `bookType + cohortId + studentId + editHash` 기반으로 만든다.

### 26.5 cover payload 변환 규칙

표지 생성은 `multipart/form-data`로 전송한다.

폼 필드 구조:

- `templateUid`: 고정 cover 템플릿 UID
- `parameters`: JSON 문자열
- 이미지 파일 또는 외부 이미지 URL 필드

예시:

```json
{
  "title": "김코드의 수료 포트폴리오 북",
  "subtitle": "SweetBootcamp Web Fullstack 5기",
  "periodText": "2026.01 - 2026.04",
  "coverPhoto": "대표 이미지 참조값"
}
```

실제 파라미터 키는 고정 템플릿 정의에 맞춰 조정한다. 중요한 점은 표지 데이터가 항상 아래 원천에서 조합된다는 것이다.

- 수료생 이름 또는 기수명
- 부트캠프명/과정명
- 수료 기간
- 대표 이미지 1장
- 사용자 편집 제목/부제 수정값

### 26.6 content payload 변환 규칙

각 페이지는 하나 이상의 블록을 템플릿 파라미터로 변환한다. 서버는 페이지 타입별 매퍼를 가진다.

예시 매퍼:

- `certificate` 페이지
  - 입력: `student.name`, `cohort.program`, `cohort.graduationDate`, `customText.certificateMessage`
  - 출력: 수료생명, 과정명, 수료일, 축하 문구

- `bio` 페이지
  - 입력: `student.bio`, `student.roleTrack`
  - 출력: 자기소개 본문, 트랙명

- `project-summary` 페이지
  - 입력: `project.title`, `project.summary`, `project.contribution`
  - 출력: 프로젝트명, 설명, 기여도

- `mentor-comment` 페이지
  - 입력: `student.mentorComment`
  - 출력: 멘토 코멘트 본문

- `photo-gallery` 페이지
  - 입력: `student.photos[]`
  - 출력: 이미지 배열

### 26.7 페이지 타입별 서버 매퍼

| 페이지 타입 | 입력 소스 | 출력 성격 |
|------------|----------|----------|
| `cover` | cohort + student + customText | 표지 파라미터 |
| `intro` | cohort + customText | 기관 소개 텍스트 |
| `certificate` | student + cohort + customText | 기념 수료 블록 |
| `bio` | student | 자기소개 블록 |
| `stack` | student.techStack | 기술 스택 블록 |
| `project-summary` | student.projects[n] | 프로젝트 요약 |
| `project-detail` | student.projects[n] | 프로젝트 상세 |
| `retrospective` | student.retrospective | 회고 본문 |
| `mentor-comment` | student.mentorComment | 멘토 평가 |
| `photo-gallery` | student.photos | 이미지 갤러리 |
| `cohort-summary` | cohort + students 집계 | 기수 요약 |
| `student-list` | cohort.students | 수료생 카탈로그 |
| `quote-page` | students[].retrospective 발췌 | 짧은 인용문 |

### 26.8 페이지 수 보정 알고리즘

1. 페이지 구성표에서 기본 페이지 목록 생성
2. `hiddenBlocks`와 사용자 편집에 따라 제외 페이지 반영
3. 결과 페이지 수가 `pageMin` 미만이면
   - `photo-gallery`
   - `quote-page`
   - `appendix`
   순으로 자동 추가
4. 결과 페이지 수가 `pageMax` 초과면
   - 부록 제거
   - 사진 페이지 병합
   - 프로젝트 상세 페이지 축약
5. 최종 페이지 수가 `pageIncrement` 배수가 아니면 마지막 보정 페이지를 추가 또는 병합

### 26.9 실패 처리 규칙

- `POST /books` 실패 시 전체 생성 중단
- `cover` 실패 시 생성 중단 후 사용자에게 표지 생성 실패 메시지 반환
- 특정 `contents` 페이지 실패 시
  - 기본 정책: 전체 생성 실패
  - 서버 로그에 실패한 페이지 타입과 원본 데이터 키 기록
- `finalization` 실패 시
  - 현재 페이지 수와 판형 규칙을 함께 반환
  - 프론트는 `페이지 수 조정 필요` 메시지 표시

| `coverTemplateUid` | `75HruEK3EnG5` | A4 소프트커버 공용 표지 템플릿 |

### 28.5 구현 판단

현재 검증 결과만 놓고 보면:
- `coverTemplateUid=75HruEK3EnG5` 는 재활용 가능성이 높다
- `contentTemplateUid=6YuhM8awvNsQ` 는 호출 형식 검증용으로는 유효하지만, 도메인 적합성은 낮다

따라서 구현 단계에서의 권장 방침은 아래와 같다.

- 1차 목표:
  - 위 `coverTemplateUid`, `contentTemplateUid` 조합으로 실제 API 호출 성공 여부를 먼저 검증한다
- 2차 판단:
  - 시각적 결과가 과제 주제와 지나치게 어긋나면, 내지 템플릿만 다른 공용 템플릿으로 교체한다
- 3차 고정:
  - 최종적으로 성공한 `coverTemplateUid`, `contentTemplateUid`를 `.env.example`이 아닌 서버 설정 파일에 고정한다

### 28.6 서버 설정 예시

```json
{
  "sweetbook": {
    "defaultBookSpecUid": "PHOTOBOOK_A4_SC",
    "coverTemplateUid": "75HruEK3EnG5",
    "contentTemplateUid": "6YuhM8awvNsQ",
    "defaultQuantity": 1,
    "pageMin": 24,
    "pageMax": 130,
    "pageIncrement": 2
  }
}
```

### 28.7 구현 리스크 명시

- 현재 고정 내지 템플릿은 `부트캠프 포트폴리오`에 최적화된 템플릿이 아니다
- 따라서 기능 검증은 가능하지만, 시각적 완성도는 추가 조정이 필요할 수 있다
- 이 리스크를 완화하기 위해 MVP 평가는 `편집 결과를 책 생성/주문 플로우로 안정적으로 연결하는가`에 우선순위를 둔다
